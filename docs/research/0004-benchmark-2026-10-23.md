# 0004: Benchmark, real Tailscale nodes in Docker

Run on 2026-10-23, on a 4 vCPU, 8 GB Linux VM with Docker 26.1.

**Setup:**

- headscale `0.29.5`, plain HTTP, embedded DERP;
- `tailscale/tailscale:stable` (client 1.104.2);
- a 128 MiB memory cap per node;
- one Docker network;
- all of it torn down afterwards.

## Results

| Measure | Result |
|---|---|
| 10 node containers launched | 0.9 s |
| All 10 online in headscale | **3.3 s** |
| Memory per `tailscaled` | 20–31 MiB |
| Memory, headscale | 23 MiB |
| `tailscale ping` between nodes | Direct between containers, 0.08 s |
| Real TCP across the tailnet (kernel TUN) | Works |
| allow-all → a deny on port 8080, seen in real traffic | ≤ 2.45 s |
| deny → allow on port 8080, seen in real traffic | ≤ 2.21 s |
| Positive control on port 22 during both changes | Stayed allowed |

The propagation times include about 0.2 s of `docker exec` overhead per
probe, so the real figures are lower.

## Traps found

1. **The official image defaults to userspace networking.** In that mode,
   outbound connections from the node to tailnet IPs silently fail. The
   first propagation measurement reported a "deny" that was really this.
   Kernel TUN mode (`TS_USERSPACE=false`, `NET_ADMIN`, `/dev/net/tun`) fixed
   it.
2. **After the control server restarted, clients forced TLS on port 443 and
   logged out**, against a lab server on plain HTTP. The lab's headscale
   needs TLS from the start.
3. **A listener that hadn't started yet looked exactly like a deny.** That's
   the case for positive controls.
4. **`tailscale debug netmap` exposes each node's compiled filter**
   (`PacketFilterRules`), which makes comparing the engines feasible.
